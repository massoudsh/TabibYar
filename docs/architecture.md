# معماری سیستم — طبیب‌یار

## ۱. اصول طراحی (قبل از هر چیز)

1. **انسان همیشه در حلقه است (Human-in-the-loop).** هیچ خروجی AI بدون تأیید صریح پزشک وارد پروندهٔ رسمی نمی‌شود یا برای بیمار ارسال نمی‌شود.
2. **AI پیشنهاد می‌دهد، پزشک تصمیم می‌گیرد.** تشخیص افتراقی، توصیه یا هشدار همیشه با برچسب «پیش‌نویس/پیشنهادی» نمایش داده می‌شود تا تأیید شود.
3. **هر تغییر در پرونده قابل ردیابی است (Audit Trail).** به دلیل حساسیت پزشکی-قانونی، نسخهٔ خام گفتار پزشک، متن تولیدشدهٔ AI، و نسخهٔ نهاییِ تأییدشده باید هرسه جدا نگه داشته شوند.
4. **داده‌های سلامت حساس‌اند.** رمزنگاری در حالت انتقال و ذخیره، دسترسی مبتنی بر نقش، و جداسازی داده هر کلینیک/پزشک الزامی است.

## ۳. شرح اجزا

### ۳.۱ کلاینت پزشک
- اپ وب (اولویت اول، سریع‌تر برای MVP) + احتمالاً موبایل در فازهای بعد.
- ورودی صوتی (ضبط حین/بعد ویزیت) یا تایپ آزاد.
- نمایش پیش‌نویس ساختاریافته با امکان ویرایش inline قبل از تأیید نهایی.

### ۳.۲ Ingestion Service
- دریافت فایل صوتی یا متن خام.
- صف پردازش (Queue) برای جلوگیری از انسداد در ساعات شلوغ مطب.
- ذخیرهٔ فایل صوتی خام در Object Storage (برای اثبات/ارجاع بعدی، نه برای پردازش مجدد خودکار).

### ۳.۳ Structuring Pipeline (هستهٔ محصول)
- **STT فارسی:** تبدیل گفتار پزشک (نیمه‌رسمی، اصطلاحات پزشکی مخلوط فارسی/لاتین) به متن.
- **لایهٔ ساخت‌دهی (LLM + پرامپت اختصاصی دامنه):** تبدیل متن خام به بخش‌های ساختاریافته:
  - شرح‌حال (Chief Complaint / History)
  - یافته‌های مهم (Findings)
  - تشخیص‌های احتمالی — **فقط به‌عنوان پیش‌نویس قابل تأیید، هرگز خروجی نهایی خودکار**
  - برنامهٔ درمان و داروها
  - توصیه‌ها و هشدارها (نسخهٔ قابل‌فهم برای بیمار، جدا از یادداشت فنی پزشک)
  - موارد پیگیری بعدی
  - نکات مبهم/ناقص → یادآوری به پزشک برای تکمیل قبل از تأیید
- خروجی این لایه یک JSON ساختاریافته است که مستقیماً وارد Clinical Data Store نمی‌شود؛ ابتدا در کلاینت پزشک برای تأیید نمایش داده می‌شود.

### ۳.۴ Clinical Data Store
مدل دادهٔ اصلی (تفصیل کامل در [wiki/data-model.md](wiki/data-model.md)):
`Patient`, `Visit`, `ClinicalNote` (raw + AI-draft + approved)، `Medication`، `FollowUpItem`، `Alert`، `Clinician`، `Clinic`.

### ۳.۵ Follow-up Engine
- در مراجعهٔ بعدی، روند علائم، تغییر دارو و پاسخ بیمار را از ویزیت‌های قبلی کنار هم می‌گذارد.
- شکایت‌های تکرارشونده و هشدارهای گزارش‌شده را برجسته می‌کند.
- خروجی: «خلاصهٔ تغییرات از جلسهٔ قبل» که پزشک قبل از شروع ویزیت جدید می‌بیند.

### ۳.۶ کانال ارتباط با بیمار
- ارسال خلاصهٔ قابل‌فهم و لیست پیگیری‌ها از طریق پیامک/واتساپ/پنل بیمار — **فقط پس از تأیید پزشک**.
- بدون ارسال خودکار محتوای تولیدشدهٔ AI بدون بازبینی انسانی.

### ۳.۷ پنل کلینیک/ادمین
- مدیریت چند پزشک، نقش‌ها (پزشک/منشی/ادمین کلینیک)، دسترسی‌ها.

### ۳.۸ Audit & Security Layer
- لاگ کامل هر تغییر روی پرونده (چه‌کسی، چه‌زمانی، چه‌چیزی).
- رمزنگاری در حالت ذخیره و انتقال، جداسازی دادهٔ هر کلینیک (Multi-tenancy).
- کنترل دسترسی مبتنی بر نقش (RBAC).

## ۴. جریان دادهٔ یک ویزیت (سناریوی نمونه)

1. پزشک بعد از ویزیت، خلاصهٔ صوتی/متنی ثبت می‌کند.
2. Ingestion Service درخواست را در صف قرار می‌دهد.
3. Structuring Pipeline متن را به بخش‌های بالینی تبدیل می‌کند و پیش‌نویس JSON می‌سازد.
4. کلاینت پزشک پیش‌نویس را نمایش می‌دهد؛ پزشک ویرایش/تأیید می‌کند.
5. نسخهٔ تأییدشده در Clinical Data Store ذخیره می‌شود؛ نسخهٔ خام و پیش‌نویس AI هم برای Audit نگه داشته می‌شود.
6. خلاصهٔ بیمار و لیست پیگیری (در صورت تأیید پزشک) از طریق کانال ارتباطی ارسال می‌شود.
7. در مراجعهٔ بعدی، Follow-up Engine خلاصهٔ تغییرات را برای پزشک آماده می‌کند.

## ۵. پیشنهاد پشته فنی (قابل تغییر توسط تیم فنی)

| لایه | پیشنهاد | توضیح |
|---|---|---|
| Backend API | Node.js (NestJS) یا Python (FastAPI) | هر دو برای این نوع سرویس مناسب‌اند؛ انتخاب بر اساس تیم موجود |
| پایگاه دادهٔ اصلی | PostgreSQL | ساختار رابطه‌ای برای Patient/Visit/Note مناسب است |
| صف پردازش | Redis Queue / RabbitMQ | برای پردازش ناهمزمان صدا و LLM |
| ذخیرهٔ فایل صوتی | S3-compatible Object Storage | با رمزنگاری در حالت ذخیره |
| STT فارسی | سرویس تخصصی گفتار-به-متن فارسی (داخلی یا API) | دقت در اصطلاحات پزشکی باید جداگانه ارزیابی شود |
| لایهٔ LLM | مدل زبانی + پرامپت‌های دامنه‌محور، با قابلیت تعویض مدل | لازم است خروجی همیشه Structured (JSON Schema) باشد |
| ارتباط با بیمار | Kavenegar/Ippanel (پیامک) یا WhatsApp Business API | بومی‌سازی‌شده برای ایران |
| احراز هویت | JWT + RBAC | نقش‌های پزشک/منشی/ادمین کلینیک |

## ۶. ملاحظات حیاتی امنیت/انطباق

جزئیات کامل در [wiki/security-privacy.md](wiki/security-privacy.md). خلاصه:
- دادهٔ سلامت بیمار باید در سرورهای داخل ایران یا مطابق با محدودیت‌های قانونی نگهداری شود (نیازمند بررسی حقوقی جدا).
- رضایت بیمار برای ذخیره و پردازش صوت/داده باید صریح گرفته شود.
- هیچ خروجی AI بدون تأیید پزشک، به‌عنوان توصیهٔ پزشکی نهایی به بیمار نمایش داده نمی‌شود.
