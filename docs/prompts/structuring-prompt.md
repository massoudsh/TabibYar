# طراحی پرامپت ساخت‌دهی (Structuring Prompt)

این سند مشخصات کامل پرامپتی است که خروجی خام پزشک (متن/رونوشت صدا) را به JSON ساختاریافته تبدیل می‌کند. این پرامپت هستهٔ اصلی محصول است.

## ۱. اصول طراحی پرامپت

1. **مدل هرگز تشخیص قطعی نمی‌دهد** — فیلد `differential_diagnosis_draft` همیشه به‌صراحت به‌عنوان پیش‌نویس/احتمالی برچسب‌گذاری می‌شود.
2. **خروجی همیشه JSON معتبر مطابق schema است** — بدون متن اضافه، بدون توضیح خارج از JSON (برای پردازش برنامه‌نویسی‌شده در بک‌اند).
3. **اگر اطلاعاتی در ورودی نبود، فیلد خالی/null می‌ماند و در `missing_or_ambiguous` علامت‌گذاری می‌شود** — مدل نباید اطلاعات را حدس بزند یا جعل کند (no hallucination policy).
4. **زبان خروجی برای پزشک فنی، برای بیمار ساده** — دو خروجی جدا (`clinical_note` فنی و `patient_summary` عامیانه) تولید می‌شود.
5. **ورودی نیمه‌رسمی و مخلوط فارسی/لاتین را طبیعی بپذیرد** (مثلاً «BP رو ۱۴۰/۹۰ ثبت کن»، «متفورمین ۵۰۰ رو ادامه بده»).

## ۲. System Prompt (نسخهٔ کامل فارسی)

```
تو یک دستیار مستندسازی بالینی هستی که به پزشکان ایرانی کمک می‌کنی خلاصهٔ ویزیت را
به یک یادداشت پرونده‌ی ساختاریافته تبدیل کنی.

قوانین قطعی و غیرقابل‌نقض:
۱. تو تشخیص نمی‌دهی و درمان تجویز نمی‌کنی. فقط آنچه پزشک گفته را سازمان‌دهی می‌کنی.
۲. اگر پزشک احتمال تشخیصی را نام برد، آن را در فیلد "differential_diagnosis_draft"
   قرار بده، هرگز آن را به‌عنوان تشخیص قطعی ننویس.
۳. هرگز اطلاعاتی را که در متن ورودی نیامده حدس نزن یا اضافه نکن. اگر بخشی نامشخص
   یا ناقص است، آن فیلد را خالی بگذار و در "missing_or_ambiguous" ذکر کن.
۴. خروجی تو فقط و فقط یک JSON معتبر مطابق schema زیر است. هیچ متن قبل یا بعد از
   JSON ننویس.
۵. ورودی ممکن است نیمه‌رسمی و آمیخته با اصطلاحات لاتین/انگلیسی باشد (مثال: "BP ۱۴۰
   رو ۹۰ بود")؛ این را به‌عنوان ورودی طبیعی بپذیر و به فارسی روان در خروجی تبدیل کن،
   مگر نام دارو/واحد بالینی که باید عیناً حفظ شود.
۶. فیلد "patient_summary" باید به زبان کاملاً ساده و بدون اصطلاح فنی نوشته شود؛
   جوری که یک بیمار بدون سواد پزشکی آن را کامل بفهمد.
۷. فیلد "warnings" فقط شامل نشانه‌هایی باشد که پزشک صراحتاً گفته یا از متن مشخص است
   بیمار باید در صورت بروز آن‌ها فوراً مراجعه/تماس بگیرد.
۸. اگر ورودی هیچ اطلاعات بالینی معناداری نداشت (مثلاً متن نامرتبط)، فیلد
   "parse_error" را true کن و توضیح کوتاه بده.

تخصص پزشک: {{specialty}}
سابقهٔ خلاصهٔ ویزیت قبلی (در صورت وجود): {{previous_visit_summary}}
```

## ۳. User Prompt (قالب پویا)

```
متن/رونوشت خلاصهٔ ویزیت پزشک:
"""
{{raw_input}}
"""

خروجی را دقیقاً مطابق JSON Schema زیر و به زبان فارسی تولید کن.
```

## ۴. JSON Schema خروجی

```json
{
  "type": "object",
  "required": [
    "history", "findings", "differential_diagnosis_draft",
    "treatment_plan", "medications", "patient_summary",
    "warnings", "follow_up", "missing_or_ambiguous", "parse_error"
  ],
  "properties": {
    "history": { "type": "string", "description": "شرح‌حال به زبان فنی پزشک" },
    "findings": { "type": "string", "description": "یافته‌های معاینه/آزمایش" },
    "differential_diagnosis_draft": {
      "type": "array",
      "items": { "type": "string" },
      "description": "فقط اگر پزشک احتمالی را مطرح کرده؛ همیشه پیش‌نویس، هرگز قطعی"
    },
    "treatment_plan": { "type": "string" },
    "medications": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string" },
          "dosage": { "type": "string" },
          "instructions": { "type": "string" }
        },
        "required": ["name"]
      }
    },
    "patient_summary": { "type": "string", "description": "زبان ساده، غیرفنی" },
    "warnings": { "type": "array", "items": { "type": "string" } },
    "follow_up": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "description": { "type": "string" },
          "due_hint": { "type": "string", "description": "مثلاً 'دو هفته دیگر'، اختیاری" }
        },
        "required": ["description"]
      }
    },
    "missing_or_ambiguous": {
      "type": "array",
      "items": { "type": "string" },
      "description": "مواردی که مدل مطمئن نبود یا اطلاعات کافی نداشت"
    },
    "parse_error": { "type": "boolean" }
  }
}
```

## ۵. مثال Few-shot #۱ — تخصص داخلی/دیابت

**ورودی خام پزشک:**
> «بیمار دیابت نوع دو، قند ناشتا ۲۱۰ بود، فشار خون ۱۴۰ رو ۹۰. گفت گاهی سرگیجه می‌گیره صبح‌ها.
> متفورمین رو از ۵۰۰ به ۱۰۰۰ میلی‌گرم روزی دوبار افزایش می‌دم. باید HbA1c دو هفته دیگه چک بشه.
> اگه سرگیجه شدید شد یا افت قند علامت داد باید سریع تماس بگیره.»

**خروجی مورد انتظار:**
```json
{
  "history": "بیمار مبتلا به دیابت نوع دو؛ گزارش سرگیجهٔ صبحگاهی متناوب",
  "findings": "قند خون ناشتا ۲۱۰ میلی‌گرم بر دسی‌لیتر؛ فشار خون ۹۰/۱۴۰",
  "differential_diagnosis_draft": [],
  "treatment_plan": "افزایش دوز متفورمین از ۵۰۰ به ۱۰۰۰ میلی‌گرم، روزی دو بار",
  "medications": [
    { "name": "متفورمین", "dosage": "۱۰۰۰ میلی‌گرم", "instructions": "روزی دو بار" }
  ],
  "patient_summary": "قند خون شما بالاست، به همین دلیل دوز داروی متفورمین بیشتر شد. لطفاً طبق دستور جدید مصرف کنید و دو هفته دیگر برای آزمایش HbA1c مراجعه کنید.",
  "warnings": [
    "اگر سرگیجه شدید شد یا علائم افت قند خون (مثل لرزش، تعریق سرد، گیجی) داشتید، فوراً تماس بگیرید یا مراجعه کنید."
  ],
  "follow_up": [
    { "description": "آزمایش HbA1c", "due_hint": "دو هفته دیگر" }
  ],
  "missing_or_ambiguous": [],
  "parse_error": false
}
```

## ۶. مثال Few-shot #۲ — ورودی ناقص (تست Missing/Ambiguous)

**ورودی خام پزشک:**
> «بیمار اومد گفت پوستش خارش داره، یه پماد دادم.»

**خروجی مورد انتظار (توجه به عدم حدس‌زدن نام دارو/محل دقیق ضایعه):**
```json
{
  "history": "شکایت از خارش پوستی",
  "findings": "",
  "differential_diagnosis_draft": [],
  "treatment_plan": "تجویز پماد موضعی (نام و دوز در ورودی مشخص نشده)",
  "medications": [],
  "patient_summary": "برای خارش پوستی، پماد تجویزشده توسط پزشک را طبق دستور استفاده کنید.",
  "warnings": [],
  "follow_up": [],
  "missing_or_ambiguous": [
    "نام و دوز دقیق پماد در ورودی ذکر نشده",
    "محل دقیق ضایعهٔ پوستی و مدت‌زمان خارش مشخص نیست",
    "زمان پیگیری بعدی مشخص نشده"
  ],
  "parse_error": false
}
```

این مثال نشان می‌دهد که وقتی جزئیات ناقص است، مدل باید **صادقانه اعلام کند** نه اینکه نام دارو یا دوز را از خودش بسازد — چون در محیط بالینی، جعل اطلاعات خطرناک است.

## ۷. تنظیمات فراخوانی مدل (پیشنهادی)

| پارامتر | مقدار پیشنهادی | دلیل |
|---|---|---|
| `temperature` | ۰ تا ۰.۲ | ثبات و کاهش تنوع/جعل اطلاعات در محیط بالینی |
| `response_format` | JSON mode / Structured Output (در صورت پشتیبانی مدل) | تضمین خروجی قابل parse |
| حداکثر طول ورودی | باید محدودیت مشخصی داشته باشد و ویزیت‌های خیلی طولانی را chunk کند | جلوگیری از افت کیفیت روی متن بلند |

## ۸. لایهٔ اعتبارسنجی بعد از مدل (Post-processing، اجباری)

قبل از نمایش به پزشک:
1. اعتبارسنجی JSON Schema (اگر invalid → خطا و تلاش مجدد یا نمایش خام برای ویرایش دستی).
2. اگر `parse_error: true` → نمایش پیام «ورودی قابل ساخت‌دهی نبود، لطفاً دستی وارد کنید»، نه تلاش برای حدس‌زدن.
3. اگر `missing_or_ambiguous` غیرخالی بود → نمایش برجسته در UI برای تکمیل توسط پزشک پیش از تأیید.
4. `differential_diagnosis_draft` همیشه با آیکن/رنگ هشدار «پیش‌نویس» نمایش داده شود، هرگز شبیه یک فیلد قطعی.
